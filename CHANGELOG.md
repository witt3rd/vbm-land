# Changelog

Interface (the stable part): the `land.conf` keys, the exit codes, the JSON last line, the hook names and the marker file names.
Additive changes to it are minor releases; anything else is major.


## 0.24.0 (minor; additive: areas, `land-pin outdated` and `update`; a repository with no `.land/areas.json` and no lock is unchanged)

- **`land-pin update` with no argument is `update --all`; `update [--all|--only NAME...] --dry-run` changes nothing** and prints the typed report of `outdated --json` plus the field `would` (`null` or `{from,to,pending_review}`), exit 0 when nothing would change, 1 when something would. An unknown argument stays exit 2; `skill update URL COMMIT SKILL...` is unchanged. `docs/pin.md` 9.2, `tests/test_outdated.sh`.

## 0.23.1 (patch; the interface is unchanged, the refusal is narrowed to where it matters)

- **The no-build guard is asked at the heavy command, not at the door.** `land-direct` used to ask `bin/no-build-guard` before anything else, so a host with a no-build marker refused even an inert landing (every changed path in `LAND_INERT`) and a reused one, which run nothing. One function, `heavy_gate`, now asks the guard immediately before the first command that can be heavy, at every site that starts one: the Tier 1 commands, every hook, the regeneration commands and `LAND_AFFECTS_CMD`. Git work (fetch, rebase, the inert and reuse decisions, the push) runs on any host. The refusal keeps exit code 2 and the guard's message, and now also says that nothing landed and nothing was pushed. A missing guard still refuses a landing that is about to run a heavy command; an inert landing does not need it. `docs/no-build-host.md`, `tests/test_no_build_host.sh`.

## 0.23.0 (minor; additive: `land-pin skill`, one lock file, one path; a consumer that does nothing is unchanged)

- **`land-pin skill add|review|adopt|update|list|verify`** (`docs/pin.md` section 8): vendoring a third-party agent skill set into `.agents/skills/<skill>/`. A skill is text an agent obeys, so it is pinned by its source URL and a FULL 40-hex commit and each skill directory by its tree hash (the one of section 1, `lib/verify.sh`); there is no signature to check, so trust is a RECORDED REVIEW (`DATE:REVIEWER`) plus the pin, and an update is a new pin and a new review. The lock is `.land/skills.lock` (`SOURCE_URL COMMIT SKILL TREE_SHA256 LICENSE_SPDX REVIEWED`, read strictly, exit 2 when malformed); the provenance of each source is `.agents/skills/THIRD-PARTY/<slug>/{SOURCE.md,LICENSE}`. `add` and `adopt` (a copy already in the tree, which must equal the commit byte for byte) write `pending` rows; `review SKILL --by NAME` records the review and refuses a skill that changed since the lock; `update` names every skill of the source, prints the files added, removed and changed, and resets the review. Exit codes: 0 done, 1 refused (a refusal changes nothing), 2 usage or a malformed lock.
- **The review aid** prints the file list with sizes, every fenced `bash`/`sh`/`shell`/`zsh`/`console` block verbatim with its file and line, and the URL hosts with their counts. It scores, classifies and decides nothing, and the tool runs nothing from a skill.
- **`land-pin verify` gains the skills step** (`land-pin skill verify`; offline and fast, it hashes local directories only): an edited, added, deleted or missing skill, a symlink, a `pending` row, a missing or disagreeing `SOURCE.md` or a missing `LICENSE`, and a directory that `THIRD-PARTY` claims and the lock does not list, each fail with the skill or file named. The tool's own skills and the repository's own are not in the lock and are not judged. A repository with no `.land/skills.lock` and no `THIRD-PARTY` is unaffected.
- `lib/paths.sh` names the lock (`LAND_SKILLS_LOCK`) and the provenance directory (`LAND_SKILLS_THIRD_PARTY`). `tests/test_pin_skill.sh` builds every source as a local git repository: no network.

## 0.22.1 (patch)

- **`land-secrets`'s hook message no longer names a tool of ours.** The pre-commit hook template, its documentation and its test said `Secrets live in doppler, never in a repository.`; a library's public-readiness lint rejects that word, so no library could adopt the gate. The message is now `Secrets live in your secret manager, never in a repository.` Nothing else changes; a consumer on 0.22.0 that copied the hook should copy it again.

## 0.22.0 (minor; additive: a tool, a template, a protected-set rule, one file and one command for the landings record; a consumer that does nothing is unchanged)

- **`land-secrets`, the secret gate** (`docs/secrets-gate.md`). The tool owns HOW: it runs the repository's pinned gitleaks over the whole history and the working tree (`--staged` for a hook), always with `--redact`, FAILS CLOSED (exit 2 when it cannot run, 1 for a finding, 0 clean), and carries a negative self-test (`--selftest`) that has been watched to fail. The repository owns WHICH (its `.gitleaks.toml`, a reason beside every allowlist entry) and pins the scanner in its `mise.toml`; the tool never vendors one. A secret found in history: rotate it first, then remove it; never allowlist a real one.
- **The pre-commit hook template** `templates/pre-commit-secrets` (copy to `.githooks/pre-commit`): runs `land-secrets --staged` from the top level and refuses the commit when it exits non-zero or cannot run. It is the early warning and a per-clone opt-in; the Tier 1 gate is the one that cannot be skipped.
- **The protected set** (`land-direct`): when `.gitleaks.toml` exists on the base, a landing that touches `.gitleaks.toml`, `.gitleaksignore` or `.githooks/*` needs a `Protected: <reason>` trailer (exit 12 without it).
- **Upgrade notes, to adopt it:** (1) `land-update`; (2) add `.gitleaks.toml` and pin gitleaks 8.x in `mise.toml`; (3) call `.land/tool/bin/land-secrets` and `--selftest` from Tier 1; (4) copy the hook template to `.githooks/pre-commit`, `chmod +x`, `git config core.hooksPath .githooks`.
- **The landings record and `land-metrics`.** Every run of `land-direct` that prints its JSON summary line also appends one typed line (`v`, `at`, `sha`, `base`, `commits`, `tier1_seconds`, `result`, `exit`, `first_commit_at`) to `<git common dir>/vbm-land/landings.jsonl`; a failed write changes neither the result nor the exit code. `bin/land-metrics` reads it and prints `landings`, `landed`, `refused-tier1` and the nearest-rank p50 and p90 of Tier 1 seconds and of commit-to-main seconds, `unmeasured` (never 0) when there is no file. `docs/landings.md`.

## 0.21.0 (minor)

- **Reuse: a base that moved in nothing the change touches is not validated again** (`LAND_REUSE=1`, default off; `LAND_AFFECTS_CMD` optional). A landing that passed Tier 1 on base B1 and meets base B2 (a lost race, or a base that moved during Tier 1) compares `B1..B2` with its own paths; with no overlap and nothing the provider relates, it pushes without running Tier 1 or the post-tier1 hook again, and the summary says `"validation":"reused"`. It fails toward running (settings directory moved, provider failed, generated file regenerated, protected path touched). What it lets through that Tier 1 would have caught is an escape, found by the release candidate. README "Reuse".

## 0.20.0 (minor)

- **The release candidate is declared, and fixed on the branch and on main.** `land-release --declare` cuts `rc/vX.Y.Z` from main's head and pushes it, so main keeps landing at full speed while the candidate runs the full suite (`--rc`). A red result is fixed with the ordinary lander on the branch (`LAND_BASE=rc/vX.Y.Z`) and the same change on main (`git cherry-pick -x`). A release from the branch reads `LAND_RC_CMD` from the branch, and is refused while the branch holds a change that is not on main (`git cherry`). A release from main itself, with no branch, is unchanged. The README states the discipline: a push to main is best-effort and no promise of a green main; go fast in development, release with caution (section 4.8).

## 0.19.2 (patch)

- **Fix:** with `LAND_INERT` set, every hook that ran AFTER the inert check failed with `timeout: invalid time interval 'M'` (a `post-tier1` hook refused the landing, an `on-run` hook silently never ran). The loop that tests a change's paths read each path's status (`M`, `A`, `D`) into `st`, which is the lander's own step-timeout variable; it now uses its own name. 0.19.0 and 0.19.1 carry the bug; a repository that set no `LAND_INERT` is unaffected. A regression case runs a `post-tier1` hook after the inert check.

## 0.19.1 (patch)

- `LAND_INERT`: a path that is DELETED or renamed away is never inert. A check can read a file's existence (a trust-ledger entry citing a document), which nothing can tell apart from its content; editing or adding an inert path is what the declaration covers. Found by deleting, and by overwriting, a consumer repository's candidate paths and running its Tier 1.

## 0.19.0 (minor; additive: three `land.conf` keys, one `land-release` flag, one optional summary key)

- **`LAND_INERT`** (new, optional): shell patterns (`*` matches `/`) for paths that no Tier 1 command, hook or reviewer reads (a changelog, prose docs). A landing whose every changed path matches, with none in `LAND_PROTECTED`, skips Tier 1 and the `post-tier1` hook; the summary line then carries `"validation":"inert"` (the key is absent otherwise, so the usual line is unchanged). A rename names both paths, so a code file moved into an inert path is still seen leaving its old one. The declaration is the project's; the release candidate audits it. A repository that sets nothing is unchanged.
- **The release candidate** (new, optional): `LAND_RC_CMD` and `LAND_RC_TIMEOUT` (default 7200 s). `land-release` runs the command, the project's FULL suite, on the exact `HEAD` with `LAND_RC=1` in its environment (nothing may be cached, selected or skipped; `LAND_INERT` does not apply) before anything is signed, and makes no tag unless it exits 0. `land-release --rc` runs it alone: no tag, no signing key. No `LAND_RC_CMD`: the release proceeds and says on stderr that the candidate was not verified by a full suite.
- The documentation now states the model it always had: landing is fast and best-effort (Tier 1), nothing runs automatically after a push, and a release is verified in full on the release candidate, with fixes landing on main until it is green (README 4.8, including the escape metric). "main is always green" and "no second tier" are gone from the README, the AGENTS block adopting repositories copy, CONTRIBUTING and two skills.
- This repository sets both: `LAND_INERT=CHANGELOG.md`, and `LAND_RC_CMD=tests/acceptance.sh --soak` (the real Tier 1 on a scratch clone with an approval committed, then 20 landers at once), which was "run by hand before a gate mechanism is rolled".

## 0.18.1 (patch)

- `run-tests-parallel`'s environment check no longer reads a filesystem with no inode table as "nearly full": it asks `df` for the inode total too and skips the inode test when there is none (btrfs reports 0 total and 0 available, so a `TMPDIR` on btrfs was refused with hundreds of GB free). `tests/test_runner.sh` has both sides, with a `df` shim.

## 0.18.0 (minor; BREAKING: `LAND_FAIL_PATTERN` is retired)

- The "inherited red" decision no longer matches a regular expression over Tier 1's output (vbm-land #6; the rule: a decision comes from typed data, never from a string match). The Tier 1 commands RECORD what failed, one name per line, in the file `$LAND_FAILED_FILE` that the lander names (a fresh file per stage, and one for the bare base's run); `bin/run-tests-parallel` records every script that failed, was missing, died, timed out or left no evidence, and a gate may append its own name. The lander compares two sets of names: every name this run recorded must also be recorded by the same stage on the base. Nothing recorded means no inheritance, as before. The words of the output decide nothing: a command that prints `FAIL x` and records nothing is not inherited (`tests/test_land_direct.sh`).
- `LAND_FAIL_PATTERN` is retired: a `land.conf` that still names it is refused by name and line, like every retired key. A repository that set it drops the line and, if it has gates outside `run-tests-parallel` whose failures it wants inherited, makes them append their name to `$LAND_FAILED_FILE`.
- `tests/test_runner.sh` has the cases (the file lists exactly the scripts that failed, a hang killed by `TEST_TIMEOUT` is listed, nothing is written without the variable); the mutation self-tests were moved to the new convention and a runner that records nothing is caught.
- Found writing it: replacing the old `inherited_red` by a slice of the script also removed the `--push` block of 0.17.0 that sat inside the slice; `tests/test_land_two_step.sh` caught it (Tier 1 ran twice and the pin stayed) before it was released.

## 0.17.0 (minor: the lander in two steps; BREAKING: `--dry-run` is `--validate`)

- `land-direct --validate` is `--dry-run`, renamed and finished: the same work (rebase, every check on the rebased tree, no push), and the commit it validated is PINNED (`refs/vbm-land/validated/<sha>`, swept after a day) and returned in the summary with the result `validated` (it was `would-land`). `--dry-run` is refused with a message naming its replacement (nothing in the family called it).
- `land-direct --push SHA` pushes exactly that validated commit, a fast-forward of the base, and runs no check again. Typed refusals, nothing pushed: `unvalidated` (exit 2: the sha is not a pinned validated commit), `moved` (exit 16: the base moved since; validate again), `held` (exit 14), `error` (exit 1: the remote refused and the base has not moved). A commit already in the base is `landed`. It exists so that a caller that decides between the steps (an orchestrator that has reviewers look at the validated tree) runs every check once on the rebased tree, never twice.
- The JSON summary (the last stdout line) carries what a caller needs to DECIDE, typed: `reason` (carried text), `log` (the failing stage's whole log), `files` (conflicted paths, a list), `base`; a `landed` summary is unchanged. A caller never needs to read stderr.
- `tests/test_land_two_step.sh` (31 cases); mutation-checked: a push of any commit (the pin lookup bypassed) and a pin kept after landing are caught. The explicit base-moved check before the push is a fast path the remote's own refusal makes redundant (the answer is the same `moved`); it is kept so a doomed push is never attempted.

## 0.16.0 (minor: how a repository adopts the ledger gate)

- The tool's Lean modules (`LandLedger`, `LandWalk`) are a small Lake PACKAGE, `land-ledger` (`lean/lakefile.toml`, with a fixed `lean/lake-manifest.json`), which a repository REQUIRES (`require «land-ledger» from ".land/tool/lean"`) instead of declaring a `lean_lib` of its own. Found the first time two adopters met: a library that declared the tool's library, vendored by a repository that declared it too, made `import LandLedger` ambiguous ("multiple packages provide distinct definitions"; Lake refuses to guess). Lake resolves a package by NAME, so the repository and every vendored library that require it get one copy. `tests/test_lean_ledger.sh` has the case (a vendored library requiring its own copy builds beside the root's). `land-check` no longer reports Lake's `.lake` build directory inside the vendored tool as drift (`tests/test_vendor.sh`: a build product passes, a stray source file still fails); `.gitignore` gets `.lake/`. A repository that declared the library itself changes that one declaration; the gate command and its keys are unchanged.

## 0.15.2 (patch: a rule that was too strict)

- `land-lean ledger` required every proved or partial claim to cite a clause whenever a clause index was configured. That is one repository's rule (every claim is about the standard, and a library's own policy is tagged `vbm:`), not everyone's: another has proved claims about the library itself that cite no clause. ## 0.15.0 (minor: a new command)

- `land-lean ledger [--write|--selftest]`: the obligation-ledger gate every Lean repository shares, replacing four hand-edited copies that had drifted (142, 157, 76 and 172 lines). The tool ships the vocabulary (`lean/LandLedger.lean`: `Status`, `Obligation` with optional clause tags and a caveat that lives with the claim, `O`, `OC`) and the gate (`lean/LedgerGate.lean`); a repository keeps only its data and a `lean_lib` line. ## 0.14.2 (patch: a bug in 0.14.0 and 0.14.1)

- `land-lean recheck` passed all the modules of `LAND_LEAN_RECHECK_MODULES` to ONE `leanchecker --fresh` run, which accepts only a single module ("--fresh flag is only valid when specifying a single module"): with two or more listed it failed every time, on a good tree too. It now runs one replay per module, side by side (each replays its whole import closure), prints one verdict per module (`recheck: M ok` / `recheck: M REJECTED` and the checker's words) and exits 1 if any was rejected. The test that was meant to prove every listed module is replayed passed for the wrong reason (the failing invocation looked like a rejection); it now also requires two clean modules to PASS and names which module was rejected, in either order.

## 0.14.1 (patch: wording)

- `land-lean recheck` said it was an INDEPENDENT kernel checker. It is not: `leanchecker --fresh` replays every declaration through Lean's own kernel code in a fresh process. It catches a declaration that reached the environment without passing the kernel (the check skipped, an option or tactic that bypasses it) and an `.olean` an honest build did not produce; it does not catch a bug in the kernel, which it shares with the build (that needs a different implementation: nanoda, not wired). The command's comment and message, `docs/lean-gates.md`, the README and the test header now say exactly that. No behaviour changes.

## 0.14.0 (minor: a new command)

- `land-lean recheck [--selftest]`: replays every proof of the modules in `LAND_LEAN_RECHECK_MODULES` (new key in `.land/lean.conf`), and of everything they import, with Lean's independent kernel checker (`leanchecker --fresh`). `--selftest` proves the gate can reject: it plants a false theorem added with the kernel check skipped, and a checker that accepts everything fails it. `tests/test_lean_recheck.sh` has 17 cases on a real toy project, mutation-checked (a no-op replay and a self-test that stops checking rejection are both caught). New payload file `lean/recheck-selftest.sh`.

## 0.11.0 (minor: additive; a repository takes it by deleting its own copies of what moved into the tool)

- **One verifier.** `lib/verify.sh` is the only code that verifies a release tag and hashes a tree (`land-update`, `land-pin`, `land-release`); a release is verified by the tree hash its signed tag records, which covers the manifest and every file (tags keep recording `manifest_sha256=` until every consumer has taken this release). `install` embeds the file verbatim, and `tests/test_verifier_one.sh` fails if the copy differs or a second verifier appears. `lib/treehash.sh` is merged into it.
- **SECURITY: `install` verifies before it reads or runs anything the release says.** Before this release `install` sourced the release's `lib/paths.sh` before checking the signature, so a hostile release's code ran even when the install was then refused, and the release could move the signers file and turn a required signature into "unverified, allowed". Both are fixed and tested. Install new repositories from the newest tag; an installer taken from an older tag still has the problem. `land-update` was not affected.
- **The test-running runtime moved into the payload**, one canonical version of what was seven hand-edited copies: `lib/ran.sh` and `bin/ran-evidence` (ran-evidence), `bin/run-tests-parallel` (with optional `TEST_TIMEOUT` and `TEST_JOBS`, abort-safe), `bin/run-scoped.sh` and `lib/reap.sh`. The copy-me `templates/run-scoped.sh` is gone. The heavy-host guard's lint checks the vendored `run-scoped.sh` beside the guard (still executed with a marker present; it must refuse). This repository's own `tests/run.sh` uses the same runner.
- **Retired paths.** `lib/retired-paths.txt` lists the files that moved; `land-check` fails a repository that holds one (a file or a link). On update: delete those copies, point their callers at `.land/tool/...`, and delete the tests of the copies, in the same commit (skill `update-vbm-land`).
- New docs: `docs/payload.md` (what the tool ships and what a repository may not copy), `docs/ran-evidence.md` (where the code lives).

## 0.3.0
- Gate-edit approvals (`lib/approvals.sh`, `docs/gate-edit-approvals.md`): a removed or changed line in a gate-defining file is accepted only on an exact diff-hash match against an approval already on the base branch. New keys, all optional: `LAND_GATE_APPEND_ONLY` (patterns of files that may only gain lines; default none), `LAND_APPROVALS` (default `scripts/gate-edit-approvals.txt`; always judged, always protected, cannot be empty), `LAND_APPROVAL_DAYS` (default 7). New: `land-direct --print-gate-diff-hash FILE [rev]` and `--print-gate-diff FILE [rev]`; the hooks see `LAND_GATE_APPROVED_FILE`; `land-direct` prints `APPROVAL COMMIT: announce to the judge before landing the edit`. Rules: approvals are read from base; an approval lands alone (its commit and its landing change no other file) and is announced to the judge before the edit; one-time (the edit's landing removes the record it uses); stale, future-dated, malformed, self-referencing and quietly removed records are refused (a fresh one is withdrawn by an `Approval-Withdrawn: FILE <12+ hex of the hash>` trailer in a landing that changes nothing else, announced to the judge); the judge fails closed. Honest limit (in the document): an agent with landing rights could write its own approval line; the control is the visible record the judge reads first. Upgrade notes: every repository now has the always-on rules for `scripts/gate-edit-approvals.txt` (it is added to the protected set automatically; a repository whose own judge or protected-paths list names its protected files should list it too); to use the approvals set `LAND_GATE_APPEND_ONLY`, or have your own `post-rebase` judge read `$LAND_GATE_APPROVED_FILE`. New vendored file `lib/approvals.sh`.

## 0.2.0
- First signed release (key and rotation: docs/signing.md; `scripts/land.signers` is the maintainer's public key).
- `land-red`: known-flaky rerun (`LAND_KNOWN_FLAKY`, `LAND_FLAKY_RERUN_WAIT`; the list is main's) and the Tier 2 freeze read from the CI runs (`LAND_TIER2_JOB`; lifts on green, never lifts a person's freeze). `land-direct`: `--group` (size budget waived for a coordinator's entries) and `LAND_LOCK_HELD=1` (the caller holds the lock; not inherited by Tier 1 or the hooks). Upgrade notes: new keys, all optional; the lock file for a coordinator is `<git common dir>/vbm-land/lock`.
- The `update-vbm-land` skill describes the pull flow: the behind report, `--diff`, `--land`, `LAND_AUTO_UPDATE`, signed releases. Convention: a release that adds or changes an interface item (key, exit code, hook, marker) carries an "Upgrade notes" line in its CHANGELOG section; `land-update --diff` prints those sections.
- `LAND_AUTO_UPDATE=none|patch|minor` (new key, default none) and `land-update --auto`: the scheduled workflow lands the newest release of the allowed class through the repository's own lander; a major never; the workflow template uses it.
- `land-update --land`: verify, stage, commit and land the update through the repository's own lander from a pristine clone of the base branch; stops on the first refusal.
- Signed releases: `bin/land-release` (signed annotated tag recording the manifest hash), `scripts/land.signers`, verification in `install` and `land-update` before anything is written or run, `install --signers`, `land-update --diff`; the PIN gains `signature=verified|unverified`.
- `land-update --check`: read-only comparison of the pin with the source's release tags (`pinned X, latest Y, behind N (patch|minor|major)`; exit 0 current, 1 behind, 3 unreachable).
- `templates/vbm-land-update.yml`: a scheduled, read-only, non-gating workflow that `install` adds when absent (drift check with `--upstream`, then `land-update --check`).
